# Review an implementation

Input (`$ARGUMENTS`): a PR number, an issue number, or nothing (= the PR of the current branch).

You are the gate between "an agent says it is done" and `main`. The implementer followed `implement-issue`; your job is to find where the result differs from what the issue, the plan and the rules demand. Do not trust the PR description - it is a claim. Evidence is the diff, the test run, and the upstream source.

Review only. Do not fix code, do not push commits, do not merge. Fixes belong to `fix-pr-comments`.

## 1. Resolve what is being reviewed

```bash
gh pr view <PR> --json number,title,body,headRefName,baseRefName,files,commits,url
```

- Given an issue number: find its PR with `gh pr list --search "<N> in:body" --state open`.
- Given nothing: `gh pr view` on the current branch.
- Get the linked issue from `Closes #N` in the PR body. No linked issue, or more than one → that is already finding number one (rules: one issue per PR).

Then read the same documents the implementer had to: the issue with its comments, `docs/unity-asset-reader-rules.md` (fully), and the relevant parts of `docs/unity-asset-reader-plan.md`.

## 2. Rerun verification yourself

```bash
gh pr checkout <PR>
npm ci && npm run verify
```

```bash
git ls-files '*.cs' '*.csproj' '*.sln'
```

Second command must print nothing (`verify` runs it too; rerun it by hand so the review does not trust the script). `packages/decoder/` touched → also run `npm test -w texture2ddecoder-wasm` with `wasm/` built. Any failure is a blocker; record the exact failing output.

## 3. Check the issue was actually implemented

Build a table with one row per **Task** and per **Acceptance** bullet of the issue, verbatim. For each row find the code and the test that satisfy it and judge:

- **met** - code exists and a test would fail if it broke. Name the test.
- **partial** - code exists but no test, or the test does not exercise the claim.
- **unmet** - missing, stubbed, or TODO.

Read the tests critically. Typical ways a test passes without proving anything: asserting only that no exception is thrown; comparing output with a golden that was generated by this same code (R12 - check how the golden file was produced and whether `scripts/make-goldens.py` (parsing) or `scripts/make-export-goldens.py` (export output) is its origin); round-tripping through our own encoder; skipping the unhappy path the issue explicitly names; `test.skip` / `todo`.

## 4. Check the diff against the rules

```bash
gh pr diff <PR>
```

Walk the Hard rules table R1–R14 one ID at a time, then the design, style and test sections. Things that are easy to miss:

- **R1/R3 licensing:** ported files carry the attribution line; nothing resembles unity-js structure or naming; `NOTICE` updated when a new upstream is used.
- **R4 browser safety:** `Buffer`, `process`, `node:` imports, also inside new dependencies. `check:browser` passing is necessary, not sufficient - it only bundles the entries that exist today.
- **R5:** an `async` or `Promise` appearing anywhere in readers, codecs or classes.
- **R6:** `Number(bigint)` conversions, `readU64` results used as `number`, pathIDs compared with `===` against number literals.
- **R7:** `.slice(` on typed arrays in the read path.
- **R8:** `package.json` diff - any dependency not in plan §1.
- **R9:** `return null` / empty result where the input is unsupported.
- **Scope:** files or features the issue did not ask for; abstractions with a single implementation; options nobody requested. Say what to delete.
- **R13:** changes under `packages/decoder/` that the issue does not call for.
- **R14:** core importing a workspace package, a feature package listing core as `dependency` instead of `peerDependency`, deep imports into another package's `src/`.

## 5. Compare with upstream

For ported logic, open the AssetStudio file named in the issue's `## Port` section (clone outside the repo, see `implement-issue` §2) and diff behavior, not text: field order, every version gate, alignment calls, signed vs unsigned reads, endianness switches, error conditions. Version gates and alignment are where ports go wrong, and fixtures built with four editor versions will not catch a wrong gate for a fifth. A missing or altered gate is a finding even when all tests pass.

## 6. Report and post

Severity:

- **blocker** - hard rule violated, acceptance unmet, verification fails, behavior differs from upstream.
- **major** - partial acceptance, missing unhappy-path test, scope creep, design rule broken without a stated reason.
- **minor** - style, naming, comments, docs.

Every finding: `path:line`, the rule ID or issue bullet it violates, what is wrong, and the concrete fix. No praise, no restating the diff, no "consider maybe". If you are unsure, check until you are sure or drop it - a wrong finding costs the fixer more than a missed nit.

Show the user the full report first (verdict, acceptance table, findings by severity). Then post it to the PR so `fix-pr-comments` can pick it up - inline comments for anything tied to a line, the verdict and acceptance table as the review body:

```bash
gh api repos/{owner}/{repo}/pulls/<PR>/reviews --method POST --input review.json
```

```json
{
  "event": "COMMENT",
  "body": "## Review: changes needed\n\n<acceptance table>\n\n<findings without a line>",
  "comments": [
    { "path": "packages/core/src/codec/lz4.ts", "line": 42, "side": "RIGHT",
      "body": "**blocker · R9** Truncated input returns a short buffer instead of throwing. Throw `Error(\"write N bytes but expected M\")` like LZ4.cs does." }
  ]
}
```

Use `"event": "COMMENT"` always: the PR author and the reviewer are usually the same GitHub account, and GitHub rejects approve / request-changes on your own PR. Put the verdict in the first line of the body instead: `Review: approved`, `Review: changes needed`. `line` must be a line present in the diff; findings about unchanged lines go in the body.

Verdict is `approved` only when verification passes, every acceptance row is **met**, and there are no blockers or majors. Finish by restoring the branch you started on (`git checkout -`).
